# Aria 开发规范

这份文档记录**怎么做改动**（流程、验证、踩过的坑），界面"长什么样"的规则在
[docs/DESIGN.md](DESIGN.md)，扩展点写法在 [docs/EXTENDING.md](EXTENDING.md)。

一句话版本：**改完跑 `npm run check`；动界面再加 `npm run smoke` + `npm run shots` 并真的看图；一次提交一件事。**

---

## 一、提交规范

- **一次提交只做一件事**，消息用中文，写清三件事：**改了什么 / 为什么 / 验证了什么**。
  例：`fix(设置): 标签框按子标题顺序重排 —— 原来物理顺序是零散的（外观排在均衡器/播放之前），
  导致点「播放与音效」落到「外观与系统」的地盘；验证：自检 161/161 通过`。
- **打包失败就不要提交"打包"那条提交**。真的踩过：某个版本打包因网络失败，
  但 `chore(打包): x.y.z` 照常提交了，于是 git 历史里有一个**从来没有产物**的版本号。
- **小改动不要打包**。`npm run dist` 只在阶段边界做（一次几分钟，产出上百 MB）。
- **自检没有全过就不出成品**。要么修到全过，要么逐条给出**直接证据**说明为什么可接受，
  并在提交信息里点明是哪几条。反例：`chore(打包): 0.1.0-beta.42` 是在 162/164 的情况下出成品的 ——
  「两次都绿才算数」这条自己写的规则没被执行。
- **不要把「检查失败」当证据去反推原因，尤其别反推「离线」**。要归因于环境，
  先**直接量一次**（`Invoke-WebRequest` / `curl` 打同一个接口），把返回码写进提交信息。
  同一个反例：beta.42 那条把两条联网自检的失败写成「本机离线导致」，
  而我从头到尾**没有量过网络**；事后实测 lrclib / deezer / itunes 全是 200，
  失败的真实形态是请求被自己的 9s 超时 abort（`This operation was aborted`）。
  归因错了就永远修不到真问题 —— 那次真正该做的是给在线请求加一次重试（见第十节）。
- **写提交信息不要用 PowerShell 5.1 的 `Out-File -Encoding utf8`** —— 它会写 UTF-8 BOM，
  BOM 会进到提交标题里（`git log --oneline` 每行前面多一个看不见的字符，本仓库曾有 39 条）。
  两道防线：① 用 `git commit -m $msg`（消息放变量里传参）或
  `[IO.File]::WriteAllText($path, $msg, (New-Object Text.UTF8Encoding($false)))`；
  ② 装一次钩子 `git config core.hooksPath scripts/git-hooks`，
  它会在提交时把开头的 BOM 就地剥掉（反向验证过：故意用带 BOM 的方式写消息文件，钩子确实剥掉了）。
- 提交前确认**工作区干净**、`npm run check` 全绿。

## 二、验证流水线（按可信度从高到低）

| 手段 | 什么时候用 | 可信度 |
| --- | --- | --- |
| `npm run check` | **每次改动必跑**：未使用 import、注入脚本语法、样式令牌、亮暗成对、左右基准线、裸值棘轮、**文档本地链接可解析** | 高（确定性） |
| 定向探针（注入代码读真实 DOM） | 验证某个具体行为（"点子标题是否滚到位"） | 高 |
| `npm run shots` | 界面改动后出截图 —— **必须打开图看**，不能靠脑补 | 高（但要看） |
| `npm run smoke` | 交互链路是否仍然可用 | 中（会抖动，见下） |
| `node scripts/probes/probe-*.js` | 数据类问题（元数据 / 歌词 / 艺人字段） | 高 |

### 自检抖动了怎么办

`npm run smoke` 结果会波动（同一提交连跑两次可能 161/161 与 159/161）。
**先判断是环境还是代码**：

1. 看日志里的 `GPU 相关行`（正常是 0）与帧率记录（开发机约 117fps）；
2. 看失败项是否**轮换**（这次是"侧栏"，下次是"灵动岛"）——轮换＝抖动，
   固定同一条＝大概是真问题；
3. 抖动多半来自**并发**：同时跑别的重活、或用脚本站连着跑好几遍。
   空载单跑一次通常就是绿。
4. **一次红掉二十几条、而且症状都像「曲库没加载」**（封面缓存 0 张、媒体墙是空的、
   歌词行数 0）→ 不是代码坏了，是**自动化档案被写坏了**：删掉 `%TEMP%\aria-dev-profile`
   再跑（会重新扫描资料库，所以第一轮偏慢）。根因通常是**自检运行中强制结束了 electron**——
   2026-10-11 这一轮我自己杀过一次，下一轮就报了 26 条假失败，删档案后立刻回到 169/169。

### 等待要用「等条件」，不要用固定 sleep

同一条检查空载时好好、一忙就红，八成是固定 sleep 等不到动画或异步落盘。
这个坑反复出现，已经修过四处：悬停过渡（等 transform 到位）、睡眠定时器复位（轮询 store 值）、
以及搜索面板的两条（等展开动画结束、等历史从主进程推回来）。
判别方法：**失败读数里带着「0×0 的矩形」「还是旧值」「数组为空」**，就属于这一类。

反过来，也不是所有断言都能靠等条件解决 —— 依赖外网的检查（歌词、艺人头像）在网络降级时
本来就会红。这类检查的断言要**精确到故障特征**，而不是笼统的"成功/失败"：
例如「缓存命中必须带 data」这条，只在**裸的 `{ buffer, mime }` 形状漏出来**时判红；
而"这一次根本没查到图"（keys 只有一个 `data` 且为 null）算环境问题、不算失败。

### 出图（`npm run shots`）的状态泄漏：DOM 与**设置**都要复位

出图是一张接一张拍的，上一张留下的东西会污染下一张。踩过两次，都是"看着像改动把界面弄坏了"：

| 泄漏源 | 症状 | 处理 |
| --- | --- | --- |
| DOM 层（视图、悬停气泡、打开的浮层、滚动位置、`:hover`） | 同一张图改动前后差 **22.97%**（其实是设置页 vs 歌曲页） | 每张之前统一清场；用 `sendInputEvent` 把**真实光标**挪到角落（`:hover` 跟真实指针走，合成事件赶不走） |
| **设置**（主题、可视化样式…存在 settings.json 里） | 27 号设成深色后，28 号也跟着拍成深色（探针 `themeSelected="深色"`） | 复位时 `await actions.setSetting({ theme: 'system', … })`；**要 await**，否则和后一张自己的设置抢时序 |

另外拍之前要**等动画真的停下**（Web Animations API 问 `document.getAnimations()`，
而不是固定睡 350ms）—— 灵动岛展开、面板入场、工具条浮出在机器忙时 350ms 不够。
复验办法：同一份代码**连拍两次**逐张比像素，21 张里应当有 17 张 ≤0.04%
（剩下几张差 0.2–0.3% 是专辑封面渲染时机与播放进度造成的，属固有噪声）。

### 自检卡住（长时间一行输出都没有）

**症状**：日志停在两百来字节，连 `=== Aria 自检 ===` 都不打印。
**原因**：自动化配置目录被写坏了 —— 最常见的是**自检运行中强制结束了 electron**。
**处理**：删掉 `%TEMP%\aria-dev-profile` 再跑（会自动重建；首次要重扫资料库，所以第一轮偏慢）。
这条提示也写在 `src/main/smoke.js` 里。

## 三、改文件的规矩（这一节最省钱）

1. **不要用 `node -e` 改文件**。PowerShell 对引号、反斜杠、模板字符串的转义规则
   和 JS 不一样，写着写着就把脚本喂坏了（本次踩了三次，每次都要重来）。
   一律：**写成脚本文件**，或者用编辑工具做**字面替换**。
   ⚠️ 2026-10 又踩了**第四次和第五次**（做示波器那一轮）：一次想用它临时删菜单里的一行做反向验证，
   PowerShell 把 `replace()` 的参数截断成语法错误 —— **脚本根本没执行，于是"验证"什么都没验**，
   而且我还按"应该已经改了"去还原文件（那个备份根本没生成）。这类"静默没生效"比报错更危险。
   现在把这条升级成硬规矩：**任何要执行 JS 的场合都不用 `node -e`，一律写 `.tmp-*.js` 脚本文件再 `node` 跑**，
   脚本里自己读文件、改、校验、必要时还原，跑完删掉。
2. **不要用 PowerShell 的 `Get-Content` / `Set-Content` / `Out-File` 改任何文本文件**
   （尤其 JSON 和含中文的源码）。两个坑会叠在一起：
   · 5.1 下 `Get-Content -Raw` 默认按 **ANSI** 读，UTF-8 的中文当场变乱码，写回去文件就毁了；
   · `-Encoding utf8` 会写 **BOM**，`package.json` 带 BOM 会让 npm 直接报 `JSON.parse` 失败。
   这条规则**原来就写在这里**（只提了 JSON 与 ANSI），结果这次改版本号时两条又一起中招：
   `Get-Content -Raw` 读出乱码 + `Set-Content -Encoding utf8` 写了 BOM，只能 `git checkout --` 回退重做。
   所以现在写死：**改文件一律用 Node 脚本**
   （`fs.readFileSync(p, 'utf8')` → 改 → `fs.writeFileSync(p, text, 'utf8')`），
   或 `.NET` 的显式无 BOM UTF-8：
   `[IO.File]::WriteAllText($p, $text, (New-Object Text.UTF8Encoding($false)))`。
   改 JSON 用 `JSON.parse` → 改字段 → `JSON.stringify(p, null, 2)`。
3. **PowerShell 里 `$name:` 会被当成盘符**。`"$f:$n"` 报错/出错值，写成 `"${f}:${n}"`。
4. **改含模板字符串的代码，用 PowerShell 单引号字符串最稳**：单引号里反引号与 `$` 都是字面量，
   `${...}`、反引号都不会被 shell 吃掉（这条是踩了四次 `node -e` 之后总结的）。
   同理，改 JSON 用 Node、改代码用单引号字符串或脚本文件。
5. 改完立刻 `node --check <文件>`；`.js` 改完再跑 `node scripts/checks/check-injected.js`
   （注入到渲染层的代码写在模板字符串里，多一个括号肉眼很难发现）。

### 不要照抄带 Context 的缩进

`Select-String -Context`（以及各种 grep 的上下文展示）会在每行前面加自己的前缀，
**那不是文件的缩进**。照着抄去做字符串替换，必然匹配不到 —— 这条连续坑了两次。

做法：替换锚点用**不含缩进的内容**（例如整行去掉前导空格后的部分），
或者先用 read 工具看一眼真实文本。

配套习惯：**先全部匹配到、再一次性写盘**。脚本没匹配全时就中止，
这样「改了 2/3」不会把文件写坏 —— 这个模式也连续兜住两次了。

## 四、代码约定（每一条都踩过）

1. **先声明后使用**。`const` / `let` 必须在引用之前 —— 把重排代码插到 `groupNodes`
   声明之前，渲染层直接 `ReferenceError`，界面整个起不来。
2. **位置计算用 `getBoundingClientRect()` 的差值，不要 `offsetTop`**。
   在多列 + `column-span` 布局下 `offsetTop` 不可靠，曾把「在线与扩展」判成「关于」。
3. **多列布局里要让块跨满整行用 `column-span: all`**。只把容器改成 `columns: 1`
   没用：`column-count` 与 `column-width` 并存时列数按宽度推算，实测仍然排成三列。
4. **搜索类组件不要写 `ui.query`**。那是"过滤资料库"的开关，写进去会把歌曲页 /
   专辑页一起改掉；页面内搜索（如设置页）自己维护状态。
5. **语义不同的历史分开存**。设置页搜索历史用 `settings.settingsSearchHistory`，
   与歌曲页的 `settings.searchHistory` 分开 —— 混用会让一边把另一边挤掉。
   有一条自检专门守这个。
6. **视图内的临时状态放模块作用域**（如 `activeSection`），不要放在每次渲染都重建的
   闭包里，否则重渲染后状态就丢了。
7. **事件监听只绑一次**。视图会渲染多次，用标志位挡住（`navScrollBound` 那种写法）。
8. **兜底要有出口**。长流程（如自检）要把结论放在 `exit` / `uncaughtException` /
   `unhandledRejection` 的兜底里，否则中途中断就什么结论都没有。

### 绘制与副作用放在状态变更之后

改完状态再画界面，顺序不要反。理由来自一次真实回归（见第十节）：
把一次绘制插在 `player.pause?.()` / `actions.setSetting(...)` **之前**，
结果那行绘制一出问题就把后面的状态变更一起挡掉了 —— 而且症状离得很远（「到点复位失效」），
查起来很费劲。

写起来就是：**先改状态，再画**；同一段里需要顺序要求时，宁可多写一行变量，也不要把绘制塞在中间。

### 函数定义在外层时，不要引用内层函数的局部变量

把辅助函数定义在 `render()` **外面**、却在函数体里用 `render` 的局部变量（例如 `const queue = playlist.queue`），
运行时就是 `ReferenceError` —— 而症状会出现在**很远的地方**：整个面板渲染不出来、某个列表显示 0 行。

写起来很简单：**把需要的东西当参数传进去**（`paintCount(queue)`），需要时再从全局来源取（`player.playlist.queue`）。

这条与「绘制与副作用放在状态变更之后」是同一类教训：**错误发生在 A 处，症状出现在 B 处**，
所以宁可多写一个参数，也不要图省事去引用外层的局部变量。

### 不要手工拼接注入代码（screenshot.js / smoke.js 里的 evaluate 模板串）

`screenshot.js` 与 `smoke.js` 里的注入代码是**嵌在模板字符串里**的，用脚本去"插入一段量测"
极易破坏它 —— 我连着两次把 `npm run shots` 弄成 `Uncaught SyntaxError`。

做法：
1. 优先用**一次性、精确到整行**的替换（锚点带完整缩进与结尾逗号），别做切片重排；
2. 改完**立刻** `node --check`；再跑一次 `npm run shots`，看到「共 N 张截图」才算没坏；
3. 坏了就 `git checkout --` 回退，保住的应该是**真正的改动**（CSS/JS），探针可以重写。

顺带一条：量测本身是好东西（本目标的错位几乎都是它先发现的），但要把它当**工具**看待 ——
工具坏了先修工具，别拿可疑的数字去改代码。

## 五、设计规范

- 界面规则以 **[docs/DESIGN.md](DESIGN.md)** 为准，改界面前先读它。
- 能机器检查的规则一律写进 `scripts/checks/check-styles.js`：
  圆角/阴影必须走令牌、`var()` 必须已定义、亮暗两套必须成对、
  **左右基准线 24px**、**裸值棘轮**（颜色/时长/字号总量只减不增）、
  **缓动只走 `--ease-*`**（`linear` 例外：进度条这类匀速动画）、
  **内联样式里不许写颜色**、**卡片必须引用同一组令牌**、
  **文件必须是 UTF-8**（见第十节「检查读的是乱码，却报全绿」）
- **新增检查的前置条件：零误报**。一条会误报的检查，第二次就会被人绕过 ——
  那还不如没有。有历史存量时用"棘轮"（只统计总量、不增加就过），
  而不是一刀切禁掉。
- 机器挡不住的部分（审美、层级判断）写进 DESIGN.md，靠截图人工看。

## 六、环境坑

| 现象 | 原因 / 处理 |
| --- | --- |
| `electron .` 退化成 Node，报 `Cannot read properties of undefined (reading 'commandLine')` | shell 里带着 `ELECTRON_RUN_AS_NODE=1`。用 `Remove-Item Env:ELECTRON_RUN_AS_NODE`（**置空不生效**） |
| `npm install` 时 Electron 二进制下载失败 | 从 `%LOCALAPPDATA%\electron\Cache\electron-v<版本>-win32-x64.zip` 解压到 `node_modules/electron/dist`，并在 `node_modules/electron/path.txt` 写 `electron.exe` |
| 打包卡在下载 | 走国内镜像：`ELECTRON_MIRROR` + `ELECTRON_BUILDER_BINARIES_MIRROR`（见 `README` 的打包说明），不需要代理 |
| Electron 版本对不上 | `package.json` 里声明的版本要与 `node_modules/electron/dist/version` 一致，否则排查时会看错版本 |
| 应用在某个目录下完全起不来 | 见下面第七节 |

## 七、排查顺序（故障 / 性能）

1. **先拿到真实报错**。不要只看"没反应"就猜；在真正的控制台里跑一次，
   `[main]` / `[renderer:error]` 会直接说是哪一行。
   （本次教训：绕了很久才去要日志。）
2. **换环境交叉验证**。"所有版本、零输出、连崩溃日志都没有"这种组合，
   优先用**另一个账户 / 另一个目录**试一次 —— 本次那个"应用完全起不来"最终
   就是靠把项目换到别的目录定位的，跟代码无关。
3. **再二分提交**。用 `git checkout <commit>` + 同一条命令复现，比读代码快。
   注意排除抖动：同一提交连跑两次，结论一致才算数。
4. **性能问题先量再改**。用 `npm run perf` 的 A/B 对照（同一轮里改 CSS），
   别凭感觉换写法；线上（开发机）帧率上限、rAF 节流都会影响读数。

## 八、别做的事（都是真实事故）

### 不要为了整洁去合并重复定义的选择器

同一个选择器在同一个文件里写多遍时，**后写的覆盖前面的**；把后面的声明并进第一处，
等于把这段声明**在层叠里的位置往前挪** —— 于是它和「夹在两条规则之间的其它选择器」的胜负关系就变了。

实测：一次把全库 18 处重复选择器合并（脚本还断言了「每个选择器按属性合并的结果不变」），
`npm run smoke` 从 **161/161 掉到 150/161** —— 聚焦块尺寸错、列表滚不动、`translateY=NaN`…
这类债务**留给需要改那条规则的人顺手清理**即可，别专门去做。

### 深度搜索的字段清单写在三处，改一处要同步三处

真正参与匹配的字段只在 `src/renderer/js/core/selectors.js` 的深度匹配那一串里定义，
但它被三个地方**描述**着：`selectors.js` 顶部的注释、歌曲页搜索面板的提示文案
（`ui/views/library-view.js` 里那句「还会搜索歌词文件，以及…」）、README 的搜索一节。

这三处没有机器守卫 —— 想做也做不了零误报的检查（文案是给人读的措辞，不是字段列表），
所以靠流程兜：**改字段时顺手把三处一起改**。历史上就漂移过：代码里早就支持
所在文件夹 / 路径 / 码率 / 采样率 / 无损，而提示与 README 只写到「目录、编码格式」。
### 自检不要拿「当前值」当「默认值」

`settingsService.get()` 读的是**当前持久化值**，而自检在同一轮里自己就会改设置 ——
把当前值当默认值来断言，就成了**自我污染**：同一份配置目录里第二次运行必然失败，
只在全新目录下才会通过。历史实例：「联网总开关」检查读 `onlineFeatures` 判默认，
而它自己在末尾把开关改成了 `false`（改成读代码默认 `DEFAULTS.onlineFeatures` 才修好）。

**判定方式：连跑两次**。这类 bug 单次通过说明不了任何问题；两次都绿才算数。
这也是判断「是代码坏了还是环境抖动」最省事的办法 —— 两次失败项一致才值得往下查。

### 截图不能当"像素级无变化"的判据

`npm run shots` 的图会随**正在播放的曲目、封面、播放状态**变化 —— 同一份代码两次出图，
PNG 也会不一样。想证明"渲染没变"，得用 `npm run audit` 的计算样式/几何对比，
而且**必须等页面加载完**（第一次基线只抓到 17 行，实际应有 810 行，那次 diff 148 处全是假警报）。

### `.select` 是包裹层类，不是加在 `<select>` 上的修饰类

正确写法：`h('div', { class: 'select' }, h('select', { … }))` —— 
配色与右侧那个箭头都由包裹层的 `.select::after` / `.select select` 提供（components.css）。
写成 `<select class="select">` 不会报错，但下拉会退化成浏览器默认样式（做睡眠定时器时踩过）。

## 十、已结案的坑（附根因，供以后遇到类似症状时对照）

### 艺人头像永远出不来：一个功能坏在五处，而自检一直是绿的

**症状**：用户反馈「歌词都能搜到，艺人头像还是搜不出来，一直是首字母占位」。
设置里 `onlineArtists` 是开着的，而主进程那条在线头像自检（`online.fetchArtist`）**始终通过**。
第二次反馈时现象更具体：**磁盘上已有缓存的那些艺人（Taylor Swift、Coldplay…）全是字母**，
没缓存的反而有照片 —— 这个反常正好指向第 5 条根因。

**五条根因，缺一不可**（后四条在备用分支 `wip/artist-avatar-online` 里早就修过，但**从没合进主线**）：

1. **渲染层根本没请求**（真正的主因）：`artwork-node.js` 的 `paint()` 里
   `if (!key) { replaceArt(node, null, ''); return }` —— 伪曲目（`artistOnly`，只有艺人名、没有 id）
   的 `artworkKey()` 返回 null，于是**在所有请求之前就返回了**。主进程再正常也没用。
   改成 `if (!artKey && !track?.artistOnly)` 放行（`resolveUrl` 对没有本地 key 的曲目本来就是走 providers）。
2. **维基解析少剥了一层**：`requestJson` 返回的是 `{ data }`，而 `artistFromWikipedia` 直接当 JSON 用
   （`payload.query.pages`）→ 永远解析不到图，静默回落到 Deezer。
3. **缓存目录名**：艺人缓存当年换到 `artists2` 就是为了绕开被污染的 notFound 负缓存，主线用的还是 `artists`。
   统一回 `ARTIST_CACHE = 'artists2'`（用户磁盘上那份还留着 10 张好图，正好复用）。
4. **图片被裁成一条**：容器是 `display: grid; place-items: center` 的圆，居中的 grid 子项里
   `height: 100%` 会被**原始长宽比**顶掉 —— 1801×2560 的照片渲染成 **140×199**，圆里只露中间一条。
   `align-self/justify-self: stretch` **也没用**。隔离实验（同一份规则 + 一张 1801×2560 的图）：
   `现状 140×199 · 拉伸 140×199 · 绝对定位 + 容器 position: relative → 140×140 ✓`。
5. **缓存命中的返回对象字段名不对**（用户第二次反馈的正是这条）：
   `readBinary` 返回 `{ buffer, mime }`，而渲染层判的是 `artistResult.data`。
   `fetchArtist` 命中时写成 `return cached` ✗，而旁边 `fetchCover` 一直是对的写法
   （`{ mime: cached.mime, data: cached.buffer, cached: true }`）—— 一眼能看出是疏忽而不是有意。
   症状最阴：**第一次打开有图，图一落盘，第二次打开反而变字母**；磁盘上早有缓存的艺人则永远只有字母。

**顺带揪出的两个「换歌手照片不换」的串台**：
6. `artworkKey()` 对伪曲目返回 null → 懒加载的去重是「节点上的 artKey === 这次的 key」，
   而所有伪曲目都是空串 → 插上第一张之后，**换到另一位歌手会被判定「图就是这个条目的」直接返回**。
   给伪曲目一个真 key（`artist:<名字>`）之后，去重 / 缓存 / 串台判断才都成立。
7. 头像加载原本写在 `if (currentDetailKey !== 'artist:…')` 里 → 同一位歌手第二次点进详情不重新观察，
   「旧版本失败过」的歌手永不重试。挪到 if 之外（`observe()` 自带 artKey 去重，重复调用无额外开销）。

**为什么自检没抓到（三处盲区，比 bug 本身更值得记）**：
- 原有检查在**主进程**里直接调 `online.fetchArtist` —— 只覆盖链路的后半段，
  而故障在**渲染层没发起请求**这前半段。
- 后补的端到端检查跑的是**冷路径**：自检结尾会清空在线缓存，于是每轮开头都是未命中，
  **缓存命中那条坏路径从来没被走到** —— 而它恰好只影响「有缓存的艺人」（用户看到的正是这批人）。
- 那条检查的断言当初写成「三位里有一位解码成功就算过」（`avatarHits.length > 0`），
  于是 Taylor Swift 挂掉、另外两位走 Deezer 成功时照样绿。
- 另一个坑：测热路径**不能用渲染层的封面服务** —— 它有自己的内存缓存，会把第二次请求挡在 IPC 之前，
  要用 `remote.online.artist` 直连主进程。

**验证方式（红-绿成对，值得照抄）**：先只加检查、不动产品代码 → 自检 **163/167**，两条头像检查都红，
读数与用户截图一致（`Taylor Swift：img=无 解码=无 用时=15141ms`，另外两位正常）；
再打一行修复 → **167/167**，读数变成
`第一次 keys=[cached,data,mime] 带data=true；第二次 … cached=true`。
最后把用户 `%APPDATA%\Aria\online-cache\artists2` 里那 10 张旧图复制进自动化档案，
用**真实缓存数据**截图确认热路径出图（验证完删掉复制品、`git checkout` 还原截图，不留痕迹）。

一句话教训：**检查要覆盖「用户看到的那条链路」，而且冷、热两种状态都要覆盖** ——
只测最容易构造的那一种，等于给故障留后门。（这条恰好印证了本文件第二节那句「两次都绿才算数」。）

### 检查自己踩自己的坑：`settle()` 用了正准备替换掉的 `setTimeout`

**症状**：睡眠定时器那条自检报「到点复位为 15（应为 0）」，看起来像功能坏了，而且连续复现两次。

**根因**：这条检查为了不等 15 分钟，把渲染层的 `window.setTimeout` 换成立即执行；
但它的等待函数是 `settle = (ms) => new Promise((r) => window.setTimeout(r, ms))` ——
**内部用的正是被替换掉的那个 `window.setTimeout`**，于是 `await settle(400)` 实际不等待。
装定时器的那次 store 订阅只要晚一个任务跑，就落到「已还原真 setTimeout」之后：
定时器被用**真的** 15 分钟延时装上、永远不到点 → 假失败。

**修法**：假定时器**一直装到断言完成**，窗口内的等待一律用提前存下的 `realSetTimeout`
（`const sleepReal = (ms) => new Promise((r) => realSetTimeout(r, ms))`），并放进 `try/finally` 保证还原。

**教训**：用替换全局 API 的方式做故障注入时，检查自己的辅助函数必须**绕开被替换的那个入口** ——
否则「注入」变成「静默失效」，症状还会伪装成功能回归。

### 在线请求没有重试：一次超时就让歌词/封面/Deezer 一起退化

**症状**：`npm run smoke` 里「在线歌词（LRCLIB）」报 `请求失败：This operation was aborted`、
「歌词来源扩展点接入」拿到 0 字符；同一轮日志里还有 `[online] Deezer 不可达，本次会话不再尝试`。

**根因**：`services/online.js` 的 `requestJson` / `requestBinary` 只有**一次**尝试，
超时一到就 `controller.abort()`（歌词 9s、Deezer 5s、iTunes/Wikipedia 8s、图片 12s），
**没有重试**。而 `This operation was aborted` 正是我们自己那个定时器报出来的 ——
冷启动的 DNS + TLS 握手、或网络降级时，第一次请求整段卡住就会这样被掐掉。
代价不只是「少一次歌词」：
- 用户第一次点开一首歌的歌词会静默失败；
- 更狠的是 Deezer 那两条路（封面 / 艺人头像）一旦失败就 `deezerDisabled = true`，
  **整个会话都不再尝试** —— 一次抖动就让封面与头像退到备选源或直接没有。

实测正常延迟（LRCLIB 搜索 5 次）：559–1469 ms，距 9s 预算很远 —— 所以失败是异常状态，不是"接口慢"。

**修法**：把两个函数合成一个带**一次重试**的 `request()`：连接层 / 超时 / 响应解析失败
重试一次（间隔 400ms），**HTTP 状态码错误不重试**（对方已经明确答复了）。
另外 404 只在 JSON 请求里当「没收录」返回，二进制请求照旧当错误（否则会把 `undefined` 写进封面缓存）。

**验证方式（值得照抄）**：不靠"读代码觉得应该会重试"，而是在 `smoke.js` 里做**故障注入** ——
把 `net.fetch` 包一层，让**第一次**调用直接抛网络错误、第二次放行，然后调 `online.fetchLyrics()`
（歌名用随机串，保证缓存 key 不命中，否则请求根本不发、检查会变成空跑），
断言「`net.fetch` 被调用 2 次」且「结果没有 error」。这条检查现在是常驻的：
`在线请求失败会重试一次（超时/网络抖动的兜底）`。

### 检查读的是乱码，却报全绿（library.css 是 UTF-16）

**症状**：`npm run check` 长期全绿，但这次为了让一条新规则生效顺手把 `library.css` 转成 UTF-8，
同一套检查的统计数字立刻变了：圆角 88 → 113、阴影 52 → 63、已定义令牌 93 → 97、
裸值 色44/时9/字5 → 色46/时9/字9。

**根因**：`library.css` 是 **UTF-16LE（带 BOM）**，而 `check-styles.js` 到处 `readFileSync(file, 'utf8')` ——
读出来每个字符后面跟一个 `\u0000`（实测 19705 个），于是所有按行/按正则的规则对它**静默失效**。
渲染没问题（BOM 在 CSS 里优先于 HTTP charset，Chromium 解得对），所以这个文件「看起来一切正常」，
只是**从没被检查过**：41KB、占全部样式表的四分之一。

**修法**：① 转成不带 BOM 的 UTF-8（解码后的文本与原来逐字节一致）；② 在 `check-styles.js` 里加第 10 条
**编码守卫** —— UTF-16 BOM / UTF-8 BOM / 含 NUL 字节，命中一条即报错并 exit 1；
③ 顺手修掉转码后才第一次被看见的裸值（两处 `#ff453a` → `var(--danger)`、`.knob__letter` 的 17px → `var(--text-headline)`），
并把 `NAKED_BASELINE.fontSize` 从 5 改成 8（另外三处是刻意的微字号：9/10/8px 塞在小控件里）。

**教训（比这个 bug 本身重要）**：**检查工具对自己读进来的东西要先做一次体检**。
一条「按行扫描」的规则，遇到不是它以为的编码/换行/结构时不会报错，只会**什么都不匹配** ——
「零问题」和「没在看」在输出上长得一模一样。同类风险还有：文件被 `.gitignore` 掉的检查、
选择器改名导致规则匹配不到（所以基准线检查在找不到规则时会**报错**而不是跳过），
以及本节第一条记录的「探针看不见隐藏视图里的同名元素」。

反向验证的方式很简单，也值得照抄：把文件改回错的编码，确认检查**真的红了**，再改回来。

### 内容区顶部那条横条：两层半透明白叠在同一个面上

**症状**：用户圈出截图「中间有一个很明显的条」—— 内容区顶部（工具栏那 52px）比它下面亮一档。

**根因**（两条一起）：
1. `.stage` 的底色是 `--bg-content`（`rgba(255,255,255,0.72)`），叠在背景光晕上合成 `(252,248,253)`；
   `.view-toolbar` 又给自己加了一层 `color-mix(in srgb, var(--bg-content) 80%, transparent)`
   （= `rgba(255,255,255,0.577)`）+ `backdrop-filter` → 合成 `(255,254,255)`，正是截图里那条的取值。
   而这条工具栏下面**从来不会有内容滚过去**（各视图的滚动容器都是它的兄弟节点），
   毛玻璃没有任何遮挡任务，纯粹是副作用。
2. 歌曲列表页的工具栏还被压成了 43px（专辑页 52px）：`.view-root` 是 flex 列，而 `.tracklist` 用了
   `height: 100%`，整列溢出后按比例压缩**所有**可压缩项 —— 工具栏 52→43、大标题 83→72。

**修法**：工具栏底色与 `backdrop-filter` 全删（吸顶只留 `border-bottom` 的 0.5px 分隔线 + 紧凑标题），
`.view-toolbar` 加 `flex: none` 锁厚度，`.tracklist` 改 `flex: 1`（与 `.browse-scroll` /
`.wall-viewport` / `.browse-detail__tracks` 一致）。

**怎么一眼看出同类问题**：截图里**同一列像素逐行扫颜色**，看有没有哪条边界上有突变
（本次：修复前在 CSS y=92 处 `(255,254,255)` 突降到 `(252,248,253)`，修复后该处无跳变）。
规则已写进 [DESIGN.md](DESIGN.md)「材料与层次」。

### sleepTimerMinutes 存不进去（已修复）

**症状**：自检里写 `actions.setSetting({ sleepTimerMinutes: 15 })` 后读回一直是 0（等 300ms、改成最多 2 秒轮询都一样）。

**根因有两层，第二层才是真的**：

1. `store.js` 里那行插错了层级 —— 我按锚点 `settingsSearchHistory: []` 插入时用了 2 空格缩进，而该锚点在 6 空格处，
   于是键掉进了别的嵌套对象，`store.get().settings.sleepTimerMinutes` 是 `undefined`，被 `|| 0` 兜成 0。
2. 更关键：`actions.setSetting` 收的是**对象补丁**（项目里一律 `actions.setSetting({ showFps: value })`），
   而我这两处写成了 `(键, 值)`：`actions.setSetting('sleepTimerMinutes', 15)` —— 传进去的字符串被当成补丁，**什么都不会发生**。
   所以功能是真坏的（下拉选什么都不存），自检也永远读回 0（它自己就没写成功）。

**修法**：两处都改成 `actions.setSetting({ sleepTimerMinutes: … })`；自检用「把 `window.setTimeout` 临时换成立即执行」的办法验到点行为（不必等 15 分钟）。
结果是 `164/164` 通过，读数从 0 变成 15。

**教训**：调用别人的 API 前先看一眼项目里已有的用法（`grep setSetting` 一下就能发现签名不同），比照着印象写快得多。

### 睡眠定时器的行内提示：绘制插在状态变更之前，把「到点复位」挡住了（已结案）

**症状**：设置行里加一句「将在 N 分钟后暂停」之后，自检里「到点复位」失效 —— 选中 15 能落盘，到点却仍为 15。
两次尝试（1 秒 interval 的实时倒计时 / 去掉 interval 的静态文字）**症状完全一样**。

**查法（这次没有第三次盲试）**：按写下来的二分方案，只加行结构、不加任何绘制调用 —— 结果 164/164 通过。
于是确定：行结构（`.settings__row-control` 里多一个 `.settings__row-value` 节点）本身无害；
元凶是**插在 `player.pause?.()` / `actions.setSetting(...)` 之前的那次绘制调用**：
它一旦出问题，就把后面的复位一起挡住（复位排在它后面，永远轮不到）。

**修法**：行结构照旧，但**每次绘制都放到状态变更之后** —— 选择变化时在挂好定时器之后再画，到点时先复位再画。
这条已经升级为通用约定（见「四、代码约定」）。
